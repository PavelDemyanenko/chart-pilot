# AGENTS.md — инструкции для ИИ-агента разработчика (ChartPilot)

Этот документ определяет правила проектирования, разработки и контроля качества для проекта
**ChartPilot** (Java 25, Spring Boot 4.1.2, Spring AI 2.0.2, PostgreSQL 16 → OpenSearch 3.10.0,
OpenSearch Dashboards 3.10.0 + AG-UI, Minikube).

---

## 1. Обязательное принятие решений через ADR

Любое нетривиальное техническое, архитектурное или протокольное решение **должно приниматься и
фиксироваться через ADR (Architecture Decision Record)** до начала написания кода.

### Когда обязательно создавать ADR
* Выбор протокола, транспорта или формата сообщений (SSE vs Streamable HTTP для MCP, формат WebSocket-фреймов).
* Изменение схемы данных, стратегии синхронизации PostgreSQL → OpenSearch (polling vs CDC, обработка удалений, маппинг индексов).
* Архитектура клиентского плагина OpenSearch Dashboards и способ его интеграции со встроенным AG-UI (`chatService`, хранение `sessionId`, обход CSP).
* Стратегия авторизации, безопасности и изоляции пользовательских сессий.
* Изменения в инфраструктуре Minikube или схеме E2E-тестирования (например, введение Mock-LLM).

### Правила ведения ADR
1. **Расположение и именование:** `docs/adr/ADR-XXXX-kebab-case-title.md` (нумерация строго последовательная: `ADR-0001`, `ADR-0002` и т. д.).
2. **Неизменяемость:** принятые (`Accepted`) ADR не перезаписываются. Если решение устарело, создаётся новый ADR со ссылкой `Supersedes: ADR-XXXX`, а у старого статус меняется на `Superseded`.
3. **Обязательный шаблон ADR:**
   ```markdown
   # ADR-XXXX: <Краткое название решения>

   * **Статус:** Proposed | Accepted | Superseded by ADR-YYYY
   * **Дата:** YYYY-MM-DD
   * **Контекст:** Какую проблему мы решаем и какие есть ограничения (технические, UX, инфраструктурные).
   * **Рассмотренные варианты:**
     1. Вариант А — плюсы / минусы.
     2. Вариант Б — плюсы / минусы.
   * **Решение:** Что именно выбрано и почему.
   * **Последствия:** Как это повлияет на код, UX, тестирование и эксплуатацию.
   ```
4. **Запрет на «тихие» решения:** если в ходе реализации нужно отойти от продуктового контракта
   (README, `docs/tools.md`) или предыдущего ADR, агент обязан сначала зафиксировать новый ADR
   и только потом менять код.

## 2. UX-стандарты использования плагина через MCP и сессию OSD

Главный критерий успеха проекта — **бесшовный UX** между терминалом (Qwen Code / OpenCode) и
браузером (OpenSearch Dashboards). Пользователь не должен думать о WebSocket, токенах, индексах
или перезагрузке страниц.

### 2.1. Zero-Friction старт сессии
* **Один клик до готовности:** `createSession()` возвращает короткий читаемый `sessionId` и чистую
  кликабельную ссылку (`http://<host>/app/home?sessionId=<id>`), которая корректно распознаётся терминалом.
* **Автоматическое закрепление сессии:** плагин OSD считывает `sessionId` из query-параметра URL при
  первом открытии и сразу сохраняет его в `sessionStorage`. При переходах по вкладкам OSD
  (Discover, Dashboards, Visualize) сессия и WebSocket-соединение **не должны разрываться**.
* **Изоляция вкладок:** использование `sessionStorage` (а не `localStorage`) обязательно — две разные
  MCP-сессии в двух соседних вкладках браузера не конфликтуют.

### 2.2. Прозрачная обратная связь в двух интерфейсах
* **В браузере (OpenSearch Dashboards):**
  * при успешном подключении WebSocket — ненавязчивый toast: *«ChartPilot MCP подключён (сессия `<id>»)»*;
  * при получении `RUN_AG_UI_PROMPT` панель чата AG-UI **раскрывается автоматически**, чтобы пользователь
    сразу видел процесс генерации и появившийся график;
  * при обрыве связи с мостом — неблокирующее предупреждение и автоматическое восстановление в фоне.
* **В терминале (ответы MCP-инструментов):**
  * все ответы `@McpTool` структурированы и понятны LLM-клиенту;
  * если браузер ещё не подключён (`WAITING_FOR_BROWSER`), инструмент возвращает не стектрейс, а подсказку:
    *«Браузер ещё не подключён. Откройте ссылку … и повторите запрос»*;
  * после успешной отрисовки `requestChart()` возвращает краткое подтверждение (что отправлено в AG-UI
    и статус выполнения run), чтобы агент в терминале мог естественно продолжить диалог.

### 2.3. Устойчивость и итеративность диалога
* **Multi-turn UX:** сессия сохраняет историю диалога; пользователь итеративно дорабатывает график
  короткими командами из терминала: *«А теперь сгруппируй по регионам»* → *«Переключи на линейный график»».
* **Контекстная осведомлённость:** `getDashboardContext(sessionId)` отдаёт актуальное состояние открытой
  страницы OSD (URL, заголовок, активный временной диапазон, если доступен).
* **Умные таймауты и reconnect:**
  * клиент OSD: экспоненциальный backoff переподключения WebSocket (1с → 2с → 4с → до 10с);
  * сервер: таймаут ожидания ответа браузера не менее 60 секунд (агрегации OpenSearch + генерация LLM),
    с корректной очисткой `CompletableFuture` при таймауте.

### 2.4. Предсказуемость и безопасность
* Если в URL и `sessionStorage` нет `sessionId`, плагин **не открывает WebSocket** и не вмешивается
  в обычную работу OpenSearch Dashboards.
* Ошибки OpenSearch, LLM или WebSocket никогда не «роняют» UI OSD: все исключения перехватываются
  плагином и транслируются в MCP-мост как `{ "status": "error", "message": "..." }`.

## 3. Инженерные стандарты и контроль качества

* **Стек:** Java 25, Spring Boot 4.1.2, Spring AI MCP Server, TypeScript (strict mode) для плагина OSD.
* **Quality gates:** SpotBugs (effort Max, threshold High) и ArchUnit (направления зависимостей,
  отсутствие циклов пакетов) обязательны в каждом сервисе; High-findings блокируют сборку.
* **Идемпотентность данных:** коннектор `pg-opensearch-connector` использует `id` записи PostgreSQL
  как `_id` документа OpenSearch, чтобы повторные прогоны не плодили дубликаты.
* **Секреты:** ключи LLM и пароли передаются только через env/секреты деплоя, никогда не коммитятся.
* **Обязательная E2E-верификация:** любое изменение MCP-инструментов, WebSocket-протокола или плагина OSD
  считается завершённым только после успешного прогона автоматизированного E2E-сьюта в Minikube
  (Playwright + MCP-клиент + PostgreSQL → OpenSearch).
